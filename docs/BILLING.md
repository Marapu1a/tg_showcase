# Telegram Stars: эксплуатация

## Включение

В `apps/backend/.env`: `STARS_BILLING_ENABLED=1`, `PUBLICATION_PRICE_STARS=30`.
Применить миграции Prisma, сгенерировать клиент и перезапустить backend и bot.
Bot `BOT_TOKEN` и backend `TELEGRAM_BOT_TOKEN` должны относиться к одному боту;
`BACKEND_INTERNAL_URL` должен быть доступен из бота.
Внешний платёжный провайдер не нужен.
Протокол: https://core.telegram.org/bots/payments-stars.

Флаг по умолчанию выключен для новых установок. Не переключать его при
незавершённых платежах: выключение снимает требование оплаты новых публикаций.

## Учёт и восстановление

Исключения для разработчиков задаются в backend через
`BILLING_EXEMPT_TELEGRAM_IDS` (числовые Telegram ID через запятую).
Ник не используется для проверки доступа. Размещения записываются с типом
`EXEMPT`, не расходуют бесплатный лимит и не создают счёт. Проверки владельца,
повторной публикации и остальные ограничения продолжают действовать.
После изменения `.env` перезапустить backend. Для проверки платного сценария
использовать отдельный аккаунт без исключения.

- `StarInvoice` фиксирует продавца, размещение, цену, срок счёта и версию
  принятых условий. Checkout проверяет Telegram-пользователя, XTR и сумму.
- `StarPayment` хранит уникальный `telegram_payment_charge_id`. Повтор события
  не создаёт вторую оплату. Лишний платёж отправляется на возврат.
- `PublicationBill` резервирует бесплатный лимит или платёж в одной
  serializable-транзакции с захватом публикации. `CONSUMED` означает отправку
  поста; `UNCERTAIN` требует проверки фактического результата в канале.
- Backend обрабатывает очередь `REFUND_PENDING` с повторами и задержкой.
  Подтверждённый возврат переводит запись в `REFUNDED`.
- Бот сохраняет события платежей на диск до доставки backend. Каталог
  `PAYMENT_EVENTS_DIR` (по умолчанию `apps/bot/.runtime/payment-events` при
  запуске через pnpm) должен быть постоянным и включённым в резервное
  копирование вместе с PostgreSQL. Не удалять очередь при обновлении.
- При недоступности backend checkout отклоняется. Уже полученные события
  повторно доставляются из очереди. Ошибки/неизвестные счета остаются в ней
  для разбора; следить за её ростом и логами.
- Если приложение закрыли после платежа, товар остаётся оплаченным
  черновиком: можно опубликовать либо вернуть Stars.
- При `UNCERTAIN` не сбрасывать статус и не отправлять пост вслепую. По
  обращению `/paysupport` проверить канал и идентификаторы счёта/платежа,
  затем согласовать запись с фактическим результатом. Автоматического
  интерфейса сверки для этого случая пока нет.

История и возвраты доступны только владельцу. Внутренние события защищены
секретом, производным от токена бота; клиент Mini App не подтверждает оплату.

## Проверки

Сборка, ESLint и 17 тестов прошли; DB-тесты используют отдельные временные
схемы. Для запуска: `RUN_DB_TESTS=1`, `STARS_BILLING_ENABLED=0`, затем
`pnpm --filter @tg-showcase/backend test` (billing-тест включает флаг сам).
Проверены конкуренция за бесплатный лимит, повторные платежи, чужие данные,
возвраты, недоступность backend и сохранение событий ботом.
Браузерный сценарий: счёт 30 XTR → подтверждение → один пост → история.
Telegram в автоматических проверках подменён; реального списания не было.
