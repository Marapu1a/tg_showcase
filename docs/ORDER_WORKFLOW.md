# Обработка заказа, отмена и возврат

Обновлено 30 октября 2026 года.

## Действия продавца

| Текущий статус | Доступные действия                        |
| -------------- | ----------------------------------------- |
| Новый          | Взять в работу; отменить заказ            |
| В работе       | Выполнен; вернуть в новые; отменить заказ |
| Выполнен       | Оформить возврат товара; вернуть в работу |
| Отменён        | Восстановить в работу                     |
| Возврат        | Отменить отметку возврата → выполнен      |

Прямой переход «Новый → Выполнен» запрещён и в интерфейсе, и на сервере. Для отмены, возврата и исправления статуса обязательна причина до 500 символов. Обычные переходы «Новый → В работе → Выполнен» не требуют лишних полей.

«Вернуть в работу» исправляет отметку о выполнении. «Оформить возврат» фиксирует возврат всего товара из заказа. Частичные возвраты пока не поддерживаются. Возврат денег согласуется вне сервиса, банковского подтверждения нет.

## Остаток

Новый заказ резервирует количество. При выполнении оно остаётся списанным. Отмена освобождает его ровно один раз. При восстановлении отменённого заказа количество резервируется заново; если его уже занял другой заказ, восстановление отклоняется.

При возврате checkbox «Вернуть все N шт. в доступный остаток» по умолчанию выключен. Для брака его не нужно включать. Включать следует только после получения пригодного для продажи товара. Отмена отметки возврата возвращает заказ в выполненные и отменяет изменение остатка, если оно было. Если освобождённый товар уже зарезервирован другим заказом, отменить такую отметку без свободного остатка нельзя.

Признак stockReleased учитывает, освобождалось ли количество именно этого заказа. Статус, остаток, версия и запись истории изменяются одной serializable-транзакцией.

## История и повторы

В карточке показаны переходы статусов с датой/временем по Москве, ролью продавца, причиной и изменением остатка. Записи не редактируются и не удаляются через API. Ошибочное действие исправляется новым действием с причиной, прежняя запись остаётся.

Для старых заказов события задним числом не выдумываются: история начинается с обновления. Дата создания и прежние данные заказа сохранены. История доступна только владельцу заказа и выдаётся по 20 событий с пагинацией.

PATCH /orders/:id принимает status, expectedStatus, expectedVersion, requestKey (UUID), reason и — только для RETURNED — restock (boolean). Версия защищает от старой вкладки даже когда статус после нескольких изменений снова стал прежним. Ключ и отпечаток действия обеспечивают идемпотентность; повтор возвращает текущий статус, не создавая новое событие и не меняя остаток.

При потере ответа интерфейс сохраняет исходное действие в sessionStorage вкладки и предлагает «Проверить изменение». Другие действия блокируются до результата. После перезагрузки можно снова найти и открыть заказ, затем проверить отправку с тем же ключом.

GET /orders/:id возвращает version и stockReleased; GET /orders/:id/history?before=<id> возвращает события без служебных ключей и отпечатков. Фильтр RETURNED добавлен в поиск; возвраты входят в завершённую историю.

## Проверка

14 тестов с включёнными проверками PostgreSQL: последовательность, обязательная причина, брак без возврата остатка, полный возврат в остаток, отмена и восстановление, нехватка товара, параллельные действия, повторы UUID, старая версия, доступ к чужой истории и пагинация. Браузерная проверка включает потерю ответа и восстановление после перезагрузки, мобильный и десктопный интерфейс. Реальные уведомления и посты тесты не отправляют.
