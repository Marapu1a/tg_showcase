# Ручные заявки

Актуальные ограничения полей, фото, запросов и восстановление после потери ответа описаны в [SECURITY.md](SECURITY.md).

## Сценарий и данные

Карточка /offers/:id: количество 1–99, контакт, необязательный комментарий. Оплаты нет. После сохранения показываем номер; локальная квитанция предотвращает случайную повторную отправку после обновления.

В /orders продавец меняет статус: NEW → IN_PROGRESS, DONE или CANCELLED; IN_PROGRESS → DONE или CANCELLED. Конечные статусы не переоткрываются. Проверяется ожидаемый предыдущий статус.

OrderRequest хранит продавца, товар, идентификатор публикации, снимок названия и цены в копейках, количество, итог, контакт, комментарий и статус. Сумма — стоимость заявки, не подтверждённая выручка. Валюта первой версии — RUB.

UUID запроса и отпечаток данных обеспечивают идемпотентность: одинаковые данные возвращают прежний заказ, изменённые данные с тем же ключом дают конфликт. Создание заказа и резервирование выполняются одной serializable-транзакцией с ограниченными повторами. Цена и доступность проверяются сервером.

Доступно = quantityLimit − reservedQuantity. NEW, IN_PROGRESS и DONE занимают остаток. CANCELLED возвращает количество один раз. Без quantityLimit остаток не ограничен. Автоматического освобождения по времени нет. Архивирование останавливает новые заявки и сохраняет историю.

## API

- GET /public/offers/:id: активная карточка без приватных данных продавца.
- POST /public/offers/:id/orders: гостевая заявка; до 20 запросов в минуту на IP и до 5 заявок на контакт и публикацию за 10 минут. IP-лимит локальный для процесса.
- GET /orders?scope=active|history|all&before=<number>: свои заявки, по 30 и счётчики.
- PATCH /orders/:id: status и expectedStatus, только владелец.
- POST /listings/photo: JPEG/PNG/WebP до 4 MB, до 25 млн пикселей, без анимации. Проверка декодирования и перекодирование в JPEG до 1600 пикселей удаляют метаданные.
- POST /listings: атомарное создание товара и черновика, защита UUID от повторов.
- GET /listings: собственные товары с публикациями, пагинация.
- GET /media/:id: публичное фото; байты хранятся в PostgreSQL.

Приватные маршруты используют подписанный Telegram initData. Гостевой контакт не подтверждён; Telegram ID от клиента не становится удостоверенной личностью. Если передан initData, проверяются подпись и срок. Перед отправкой есть пояснение о передаче контакта продавцу.

## Уведомления и публикация

Заявка и PENDING сохраняются вместе. При обычном запуске API обработчик каждые 5 секунд забирает очередь и временно закрепляет запись за собой. До пяти попыток с увеличивающейся задержкой; затем FAILED видно продавцу. Сбой Telegram не отменяет сохранённую заявку.

Доставка допускает повтор: если Telegram принял сообщение, а сохранение результата не удалось, продавец может получить тот же номер снова. Новый заказ при этом не создаётся.

Публикация защищена состояниями IDLE/SENDING/SENT/UNCERTAIN. Параллельный запрос не отправляет второй пост. Явный отказ Telegram разрешает повтор, неизвестный результат блокирует слепую повторную отправку. Восстановление UNCERTAIN и зависшего SENDING ещё не вынесено в интерфейс.

## Проверки

В PowerShell из корня:

```powershell
pnpm build
pnpm lint
$env:RUN_DB_TESTS='1'
pnpm --filter @tg-showcase/backend test
Remove-Item Env:RUN_DB_TESTS
```

Интеграционный тест создаёт временную схему в БД из apps/backend/.env, применяет миграции и удаляет только эту схему. Нужны права CREATE SCHEMA. Telegram замещён, реальные сообщения не отправляются. Без RUN_DB_TESTS проверка PostgreSQL пропускается.

Ручная проверка: новый товар с фото и остатком 3 → публикация в своём тестовом канале → заявка на 2 → номер, остаток 1, уведомление и запись продавца → взять в работу → выполнить → проверить историю. Отдельно проверить отмену и возврат остатка. Ручной сценарий создаёт реальные записи и сообщения.
